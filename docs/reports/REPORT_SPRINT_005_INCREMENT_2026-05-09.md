## Постановка задачи для этого инкремента

Спринт 5 по плану охватывает полный функционал корзины: добавление, изменение количества, удаление, расчёт суммы, локальное сохранение, синхронизацию с сервером для авторизованных пользователей, именованные use cases на каждую операцию.

Указано выполнять работы **«по лайту»**, то есть первым шагом нужно было получить **сквозной рабочий MVP-поток** без раздувания объёма:

1. Чтобы кнопка «Добавить в корзину» на экране товара реально меняла содержимое корзины.
2. Чтобы экран корзины мог загрузить данные из общего источника и показать строки, суммы и действия (включая очистку).
3. Чтобы идентификатор пользователя для корзины согласовывался с уже реализованной локальной авторизацией (гость vs залогиненный профиль).

Более тяжёлые пункты (Room как постоянное хранилище корзины, отдельные use case-классы, серверная синхронизация) сознательно **отложены** на следующие подходы в рамках того же спринта.

## Что было до изменений (диагностика)

Перед началом работ выяснилось следующее:

1. **Интерфейс `CartRepository` существовал в domain**, но **не было реализации и регистрации в Koin**. При этом `CartViewModel` уже ожидал `CartRepository` через dependency injection. Это классический «контракт без реализации»: экран корзины потенциально не мог стабильно подниматься без падения DI или заглушки на этапе старта фичи.

2. **`CartModule` регистрировал `CartViewModel` как `single`**, что некорректно для Android `ViewModel`: жизненный цикл должен быть привязан к экрану/графу навигации, а не к singleton-приложения. Это могло приводить к устаревшему состоянию и неожиданному поведению при повторном входе на экран.

3. **`ProductDetailViewModel` содержал TODO по Спринту 5**: добавление в корзину сводилось к логированию и события UI без записи в доменный слой.

4. **На экране корзины** уже был развитый Compose-UI (список, +/- количество, удаление, блок итогов), но **в строке промежуточной суммы была явная ошибка форматирования** (лишний символ после `String.format`), а валютные обозначения смешивались (`₹` и ₽). Это мешало воспринимать экран как «готовый к демонстрации заказчику».

Именно эти точки и взяты в работу в первом инкременте.

## Принятое архитектурное решение

### In-memory `CartRepositoryImpl`

Для минимального времени внедрения и отсутствия миграций Room в этом коммите выбрана **реализация корзины в памяти процесса** (`ConcurrentHashMap` по `userId`). Это:

- позволяет без изменения схемы БД и версии Room закрыть сценарий «добавили → увидели в корзине → изменили количество → удалили → очистили»;
- сохраняет контракт `CartRepository` и текущий код `CartViewModel` почти без переписывания;
- чётко ограничивает область ответственности: **данные не переживают перезапуск приложения** — это зафиксировано как сознательное ограничение до следующего шага.

Дальнейший перенос на Room (таблицы `carts` / `cart_products` уже намечены в модуле local как сущности) не ломает контракт репозитория: достаточно заменить реализацию и сохранить семантику методов.

### Привязка к текущему пользователю

Используется уже существующий **`GetCurrentUserUseCase`**:

- если пользователь **не авторизован**, для корзины используется условный идентификатор **`userId = 0`** (гостевая корзина);
- если пользователь **авторизован**, берётся **`UserProfile.id.toInt()`** как ключ корзины.

Таким образом корзина гостя и корзина зарегистрированного пользователя **разделены**, что соответствует ожидаемому UX после внедрения регистрации в Спринте 4.

**Замечание по типам:** в доменной модели профиля идентификатор — `Long`, а в контракте корзины исторически используется `Int`. Для текущего масштаба демо-данных это приемлемо; при росте идентификаторов потребуется унифицировать тип в `CartRepository` и связанных моделях.

### Экран товара

`ProductDetailViewModel` получает `CartRepository` и при добавлении:

- учитывает **выбранное на UI количество**;
- ограничивает его **остатком на складе** (`product.count`), чтобы не добавлять нереальное число единиц.

Это небольшое, но важное улучшение предсказуемости поведения корзины.

## Поведение для пользователя и заказчика (как проверить)

1. Открыть каталог, перейти в карточку товара, выбрать количество, нажать **«Добавить в корзину»** — появляется snackbar об успехе.
2. Открыть **корзину** из верхней панели / навигации — отображаются позиции с изображением и ценой в рублях, доступны **+ / −**, **удаление строки**.
3. Нажать **«Очистить корзину»** — список опустошается, показывается пустое состояние с переходом в каталог.
4. **Без входа в аккаунт** корзина принадлежит гостю (`userId = 0`).
5. **После входа** корзина строится отдельно для id пользователя (до следующего шага синхронизации гостевой корзины с аккаунтом объединение не выполнялось — см. ограничения).

## Известные ограничения и технический долг (явно)

1. **Корзина не сохраняется после перезапуска приложения** — только оперативная память процесса.
2. **`CartRepository` API возвращает `Flow` из `suspend`-функций** — исторический стиль; допускает упрощение до обычных `suspend` без потока там, где достаточно одной эмиссии.
3. **`Int` для userId в корзине и `.toInt()` от `Long` профиля** — ок для демо, потребует ревью перед продакшеном.
4. **Нет переноса гостевой корзины в пользовательскую** при логине — отдельная UX-задача.
5. **Именованные use cases** из плана (`AddToCartUseCase`, …) пока не выделены — вызов идёт из ViewModel напрямую в репозиторий; это нормально для инкремента, но для единообразия со слоем domain их можно добавить тонкими классами без изменения UI.

## Следующие шаги в рамках Спринта 5 (рекомендуемый порядок)

1. **Room**: DAO для корзины, миграция при необходимости, замена `CartRepositoryImpl` на локальную реализацию с тем же контрактом.
2. **Перенос гостевой корзины при логине** (merge по `productId`).
3. **Выделение use cases** под операции корзины и регистрация в `DataModule` для симметрии с авторизацией и каталогом.
4. **Синхронизация с API** (когда появится backend) — отдельная ветка поверх локального SSOT.
5. **Тесты**: unit на `CartRepositoryImpl` (слияние количеств, удаление, очистка) и на `CartViewModel` с подставным репозиторием.
